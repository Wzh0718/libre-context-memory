# 02 · 架构：核心引擎 + 适配层

> 量化基准见 `01-data-evidence.md`。成本当量模型：`当量 = fresh + 0.1 × cached`（Codex 现状 916M）。
> 2026-09-11 定调：**不走中转站，全部能力在 agent 框架内（插件/hook），跨 harness 可移植。**

---

## 1. 为什么拆「核心引擎 + 薄壳」

- hook/插件寄生在 harness 生命周期里，**没法单测**；但压缩、提取、检索都是纯逻辑，必须脱离 harness 可测
- 三家 harness 的口子契约完全不同，但**压缩器、句柄、记忆库可以只有一份**
- 用户会切换 harness（Codex → DSH → CC），能力不能绑死在任何一家

```
核心引擎（本地 CLI：stdin/stdout JSON，进程无关）
  ↑ 被调用
适配层薄壳（事件名映射 + 字段提取 + 失败静默，除此之外没有逻辑）
  ↑ 挂在
harness 事件（DSH 插件口子 / CC hooks.json / Codex hooks.json）
```

## 2. 跨 harness 能力矩阵（设计必须按最差交集思考）

| 能力 | DSH 插件 | CC hook | Codex hook |
|---|---|---|---|
| 工具输出入库前压缩/替换 | ✅ `toolResultPruner` + `spillStore` | ✅ `PostToolUse` 可替换输出 | ⚠️ 依赖 `block+feedback`，**未验证** |
| 命令源头改写 | 插件可包装 | ✅ `PreToolUse.updatedInput` | ⚠️ 未验证 |
| 折叠前提取记忆 | ✅ compaction seam | ✅ `PreCompact` hook | ⚠️ 接口形态待确认 |
| 会话开始/提问时注入记忆 | ✅ request-context 注入 | ✅ `SessionStart`/`UserPromptSubmit` | ✅ `SessionStart` |
| 会话结束归档 | ✅ | ✅ `Stop` | ✅ `Stop` |
| 缓存/usage 观测 | ✅ | ❌ 基本没有 | ❌ 基本没有 |

**纪律：核心引擎对适配层只做能力探测，不做能力假设。** 拿不到 usage 的 harness 就关掉对应计量与「击穿检测」，降级不报错。

## 3. 插件层能治什么、不能治什么

| 病灶（实测） | 插件层手段 | 预期收益 |
|---|---|---|
| 工具输出长尾：0.30% 调用占 55.5% 体量，沿用体积 1.42B est | 入库即压缩「摘要+句柄」（03 文档） | 上下文工具输出体积 −50%+（保信息） |
| DSH 压缩极少（15 次/21 会话，prune 单次仅 2–13k） | prune 策略激进化 + compaction seam 挂提取器 | 每次折叠降 30%+ |
| DSH 静态地板 33k est/请求（skills 12.4k + 工具 15.1k） | 大块稳定内容引用化：目录索引 + 按需加载 | 地板 −60% |
| 记忆注入变体打前缀（8 个哈希变体） | 注入统一为尾部稳定块 | 消除人为前缀断裂 |
| 跨会话重复探索 | 记忆层（04 文档） | 对照实验量化 |
| ~~Codex 缓存击穿 455M fresh~~ | **排除出范围**（中转站/框架侧的病，用户自行关闭） | — |
| reasoning 回传疑似前缀杀手 | 排除（需 wire 数据，中转站层） | — |

## 4. 量化预期（插件层口径重算）

```
插件层直接收益 = 工具输出体积压缩（增量 −50%+）
              + 折叠提前与 prune 激进化（每次 −30%+）
              + DSH 地板引用化（每请求 −20k est 量级）
间接收益     = 历史体积小 → 缓存击穿/折叠时全价重发的绝对损失同比例变小
```

「击穿即压缩」降级为**仅 DSH 可用**（只有 DSH 插件拿得到 usage/fresh 突增）；CC/Codex 上压缩只挂在 harness 自己的折叠时刻。

## 5. 测量纪律（最重要的一条，不变）

**把「新增内容」和「重发内容」分开计量**：

| 指标 | 定义 | 期望 |
|---|---|---|
| 缓存命中率 | cached / (fresh + cached)，仅 DSH 可测 | ↑ |
| fresh/请求 | 中位 / p90 | ↓ 现 6,671 / 91,140 |
| 上下文当量 | fresh + 0.1×cached（按会话） | ↓ |
| 每请求新增 | 哈希去重后的新内容 est | **持平**（真实工作，不该被压） |
| 压缩比 / 回取率 | 核心引擎 meter 自埋点 | 见 05 记分卡 |

只盯总量会被误导——「图片内联」假设就是被总量误导而证伪的实例。

## 6. 贯穿全局的三条纪律

1. **历史只在两个时点被改写**：入库那一刻 / 缓存击穿或折叠时刻。其余任何时刻动历史 = 前缀断裂 = 下一轮全价，越优化越贵
2. **句柄内容确定性生成**：同输出同句柄、同一路径（同一 hash），可缓存可复用
3. **压缩本身也受重发定律约束**：实测 DSH compaction 调用近全价（180k 输入仅 5.4k cacheRead）→ 压缩不许「定期执行」，必须挂在折叠/击穿时刻，一次全价办两件事
