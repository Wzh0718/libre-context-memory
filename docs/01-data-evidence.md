| 指标 | Codex | DSH |

## 2. Codex 高消耗点（按影响排序）

### ① 工具输出长尾 —— 0.30% 的调用占 55.5% 体量

| 指标 | 实测 |
|---|---|
| 工具输出总量 | 27,724 次 |
| 分位 | p50 **1,704 字符** / p90 19,865 / p99 40,645 / **max 7,723,459** |
| >100k 字符的调用 | **84 次（0.30%）= 55.5% 全部工具输出字符** |
| 按工具 | `exec` **81.9%** ｜ `exec_command` 16.6%（合计 98.5%） |
| 失控原因 | 84 次大输出中 **76 次未设 `max_output_tokens`**（其余 8 次设了仍被突破） |

> **2026-09-11 Phase 0 回放重大修正**：94 个 >100k 输出（共 223.5M 字符）中 **99.9% 是 base64 内联数据，且 94/94 全部含有**。
> → 长尾的本质不是「日志太长」，而是**工具输出内嵌了图片/二进制**（如 exec 截图回传）。确定性处理（剥离 base64 → 占位符 + spill 句柄）即可吃掉长尾的几乎全部体量。见 `reports/phase0-compression-report.md`。

### ② 缓存击穿 —— 17.5% 的请求吃掉 72.1% 的 fresh

- fresh >50k 的请求 4,515 个 = 512.7M fresh；其中 **4,039 次前缀未变、无新内容 = 455M（64%）**
- **仅 11% 的会话命中率 >90%**；与时段无关；64.3% 单发、最长连续 12 次
- **早期断裂**：1,525 个请求只匹配 1,920–3,456 tokens 缓存前缀（100.9M fresh）→ 断裂点在**系统提示区（前 2–3k tokens）**，不是历史区

### ③ 压缩太晚、太少

- 313 会话仅 354 次压缩；触发中位 **224,616 real**（窗口 258,400 的 **87%**）
- 压缩后中位仍 **140,145 real**（降 32.2%）

### ④ 其他

- >200k 上下文命中率跌到 65.7%
- reasoning 回传 933,931 段（疑似每请求重新加密 → 早期断裂嫌疑，**需 wire 验证**）
- 会话首请求 ~27k real（不可避免，合计仅 5.1M fresh）
- **附件/图片不进上下文**（已证伪为优化目标）

## 3. DSH 高消耗点（按影响排序）

### ① 静态地板 33k est（≈62k real）/请求，91% 是静态内容

| 构成 | est/请求 | 备注 |
|---|---|---|
| 工具定义 | 15.1k（17.0%） | 72 个工具；396 请求仅 89 个唯一哈希 |
| skills 目录 | **12.4k（16.1%）** | 单块 10 万字符；**8 个哈希变体**，变体切换 = 前缀失效 |
| system prompt | 2.8k | 全程恒定 |
| 记忆注入 | 2.9k | 2,356 段 / 99 唯一哈希 |

### ② tool_result 累积 37.8%

`bash` 37.8% ｜ `read` 31.9% ｜ `mcp__codegraph__*` 21.0% ｜ `skill` 5.5%
单次最大仅 5 万字符（DSH 有截断；Codex 最大 772 万字符，**154 倍**差距）。

### ③ 压缩极少（更正：非零）

`context_operations` 15 行（21 会话中仅 2 个会话触发）：13 次单条 prune（每次只 shadow 2–13k tokens）+ 2 次完整 compaction（分别 shadow 174k / 128k tokens）。
**附带发现：compaction 调用本身几乎全价**——180k 输入仅 5.4k cacheRead、148k 输入仅 13.8k cacheRead，压缩请求自身也在全价重发 →「更频繁压缩」不是免费策略，应挂在缓存击穿时刻执行。
整体仍线性涨到 161.9k est（≈305k real），逼近 272k 窗口。

### ④ fork 子代理

45k fresh/请求（主循环 6 倍）、命中 7.5%、继承上下文 101.5k est 比主循环还大、最差单笔 292,864 fresh。

### ⑤ 其他

- 供应商击穿 3 次 / 466k fresh（前缀逐字节稳定仍全价）
- 记忆注入变更时 fresh 升高概率 13% vs 4%

## 4. 已验证 / 已证伪 / 待验证假设

| 状态 | 假设 | 结论 |
|---|---|---|
| ✅ 已验证 | 请求间上下文纯追加 | DSH 352/352 请求前缀稳定 |
| ✅ 已验证 | Codex 每请求新增内容很小 | 中位 679 est |
| ✅ 已验证 | `token_count.input_tokens` 含缓存 | 采集中已归一化 fresh = input − cached |
| ❌ 已证伪 | 附件（截图等）被计入 token | 31 个附件 79.2MB **未进上下文**，仅落盘 |
| ⚠️ 需修正 | 「图片内联」不是优化靶心 | **附件路径确实不进，但工具输出内联 base64 进**：94 个 >100k 输出 99.9% 字符是 base64（223.3M/223.5M），是长尾本体，升为**头号确定性优化靶心**（2026-09-11 回放实测） |
| ⚠️ 待验证 | reasoning `encrypted_content` 每请求变化 → 早期断裂 | 断点恰在系统提示后第一个 item（1,920–3,456 tokens），**需 wire 数据** |
| ⚠️ 待验证 | 会话被路由到不同上游密钥 → 缓存池分裂 | 系统性的低命中（仅 11% 会话健康）指向此，但需中转站侧确认 |
| ⚠️ 待验证 | Codex PostToolUse payload 带 `tool_response` 且 block 可替换结果 | DSH 镜像契约如此，真机需探针 |

## 5. 估算校准（分析口径）

- 采集用 chars/4 估算；**实际/估算比：Codex 1.31×（英文/代码）、DSH 1.88×（中文多）**
- 报告数字以 est 标注时需注意换算；以 real（usage 实测）标注时为计费口径
