# 06 · 价值记账（`lcm value`）设计

> 目标：把「这个工具到底值多少」从模糊的载荷百分比，变成账本上可复核的硬账。
> 对齐 05 记分卡口径：**每任务成本当量 = fresh + 0.1 × cached**。
> 2026-09-15 设计；试算已在真实台账（4673 请求 / 343 次臂动作 / 70 会话）上跑通。

---

## 1. 为什么现有 report 看不出价值

三种价格混在一个数字里，且最值钱的一块（避免的击穿）根本没记账：

| 价格档 | 谁在这一档 | 特征 |
|---|---|---|
| **1.0× fresh** | 压缩臂 reshape 的内容、冷窗口重建时的载荷 | 落在请求里的新内容，全额计价 |
| **0.1× cached** | 剪枝/折叠瘦身后的历史 | 折价，但**每轮请求都重带** → 靠后续请求数放大 |
| **0（设计避免）** | 热窗口改写（piggyback 拦下） | 若真做了 = 整段前缀全价重发一次 |

实测分布（真实台账 4525 请求）：缓存命中 95.0%；**fresh 花费 50% 集中在 77 个请求（1.7%）**、
90% 集中在 281 个（6.2%）；击穿（fresh>50k）214 次（4.7%）。
→ 稳态几乎不花钱，钱在尾部；不同臂打的是不同的档，必须分开算。

## 2. 三类价值：必须分开标注

| 类别 | 含义 | 记账规则 |
|---|---|---|
| **realized** | 已实现：臂动作直接减少的载荷，按档计价后累加 | 计入净节省 |
| **avoided** | 避免的损失：piggyback 让改写落在冷窗口，省下「若在热窗口做」的全额重发 | **单列，不计入净节省**（未实现的机会成本） |
| **estimated** | 估算：记忆臂减少的请求数 × 平均请求成本 | 单列，标注估算依据与样本量 |

**纪律**：报告里每个数字都要能回答「数据从哪来、样本多少、口径是什么」。

## 3. 数据来源（全部来自现有 meter，无需新埋点）

| 臂 | 事件 | 关键字段 | 状态 |
|---|---|---|---|
| 压缩 | `kind:'compress'` | `originalChars` / `compressedChars` / `sessionId` / `ts` | ✅ 已有 |
| 剪枝 | `kind:'prune'` | `charsBefore` / `charsAfter` / `nodes` / `tokensBefore` / `sessionId` | ✅ 已有 |
| 折叠 | `kind:'fold'` | `charsBefore` / `charsAfter` / `nodes` / `watermark` | ✅ 已有 |
| 静态裁剪 | `kind:'static-trim'` | `savedChars`（**当前未记**，需补） | ⚠️ 补埋点 |
| 记忆注入 | `kind:'memory-inject'` | `chars` / `entries` / `profile` | ✅ 已有 |
| 计费真相 | `kind:'usage'` | `input`（fresh）/ `cacheRead` / `hitRate` / `cacheBust` | ✅ 已有 |
| 会话事件 | `kind:'compaction'` | `op` / `shadowedTokens` | ✅ 已有（用于识别冷窗口） |

关键 insight：`usage.input + usage.cacheRead` **就是那次请求的实际载荷**——
反事实模型不需要额外埋点，直接用真实轨迹推。

## 4. 模型

按会话分组、按 ts 排序，逐请求累加（**review 修正版**，已实现于 `core/value.mjs`）：

```
对每个会话 S：
  L = 全部会话「compaction 事件前最近一次 usage 载荷」的中位   ← DSH 内置压缩的实测触发水位
  ceiling(S) = max(S 实际最大载荷, min(L, 模型窗口 − 输出预留))
  active = 0
  对 S 内每个 usage 请求 u（按时间序）：
     把 ts ≤ u.ts 的臂动作累加进 active
     room  = max(0, ceiling − 实际载荷(u))
     delta = min(active, room)                                ← 夹窗口
     price(u) = 1.0（u 是击穿请求：cacheBust 或 fresh ≥ 50k）
                否则 = cacheFactor
     定价（review 修正——首版把 delta 按 1.0× 计入每个后续请求，虚高约 7 倍）：
       prune/fold：被剪内容早已在缓存前缀里 → 按 price(u) 计
       compress：reshape 的内容在无臂世界会作为新内容进下一个请求
                 → 首个后续请求按 1.0×，之后按 price(u) 计
     realized(u) = Σ_臂 attributed × 档价（按动作 ts 序老者先填充 room 归因）
  实际成本   += input + cacheRead × cacheFactor
  反事实成本 += 实际成本 + realized(u)

净节省 = 已实现节省 − 注入开销（同会话首次 1.0×、重复折价）
avoided（单列）= Σ_臂动作 (动作前最近一次 usage 的载荷)
estimated（单列）= 静态裁剪中位节省/请求（全局事件，无 sessionId，无法归因）
```

### 为什么必须夹窗口 + 必须按档计价（两次试算踩到的坑）

**坑一（不夹窗口）**：算出「节省 243.9M > 实际花费 131.1M（186%）」——不可能。
根因：被剪掉的内容在「无臂」世界里也会超出上下文窗口，根本不会被发送。

**坑二（定价错误，review 发现）**：夹窗口后算出 54.8%，但 delta 被按 1.0× fresh
计入**每一个**后续请求。实际上未被剪掉的内容躺在缓存前缀里，后续请求只付折价
（95% 命中率下均价 ≈ 0.145×）。修正后：

```
实测（已实现 core/value.mjs，140 真实会话 / 4941 请求，provenance 过滤后）：
  实际成本当量 140.2M ｜ 反事实 165.1M ｜ 净节省 24.9M = 15.1%（占反事实）
  压缩臂 6.7M ｜ 剪枝臂 18.2M ｜ 折叠臂 0（从未 active）｜ 注入 0（shadow 期）
  避免的击穿 70.9M（单列）｜ 反事实水位 242k（1895 次 compaction 实测中位）
  被窗口夹住的请求 1186 个
```

交叉验证：bench-all 载荷口径 11.9% vs 本模型 15.1%——同向、同量级 ✓
（差异来源：成本当量里压缩臂按 1.0× 计的首个承载请求权重更高，载荷口径则等权）。

### 模型的自证不变量（已写成测试，`core/test/value.test.mjs` 17 个）

1. **反事实 ≥ 实际**（逐请求由构造保证，总量断言）
2. **节省 ≤ 反事实成本**（否则必是重复计数）
3. **每请求 delta ≤ ceiling − actualPayload**（夹窗口生效）
4. **无臂动作时节省恰为 0**（空输入 → 零输出）
5. **确定性**：同输入同输出（账本可复核）
6. **单调性**：多加一个臂动作，节省不减少
7. **定价正确性**：prune 在命中请求按折价、击穿按 1.0×；compress 首个承载请求
   按 1.0× 之后按档；注入首次 1.0× 重复折价
8. **provenance**：sessionId 不在 sessionsDir 真实会话集合里的事件被排除
   （`~/.lcm/meter-000000.jsonl` 等合成/基线数据不混入台账）
9. **交叉验证门**：与 bench-all 载荷口径必须同向、同量级——首版 54.8% vs 11.9%
   差了 4.6 倍，正是这道门抓住了定价 bug

## 5. 归因边界（诚实声明）

- 本模型算的是 **lcm 单独贡献的上界**：反事实里假设内容一直留在历史中。
  实际上 DSH 内置上下文管理也会动手（实测 `compaction` 事件 337+ 次）——
  没有 lcm 时，内置压缩会更早/更频繁触发，真实反事实低于本模型。
- 因此报告必须写明：「上界口径（未扣除内置机制的反事实影响）」。
- 交叉验证：与 `scripts/bench-all.mjs` 的载荷口径对比——同一批会话里，
  「载荷减少 %」与「tok-当量减少 %」必须同向且量级可比，否则模型有 bug。

## 6. 输出形态

```
$ lcm value [--days 7] [--cache-factor 0.1] [--json]

价值记账（真实台账 · 近 7 天 · 4673 请求 / 343 次臂动作 / 70 会话 · 折价因子 0.1）
  实际成本当量    131.2M   （fresh 44.1M × 1.0 + cached 869M × 0.1）
  反事实（无 lcm）290.3M
  ── 已实现节省 ───────────────────────────────
  ① 压缩臂（1.0× 档）      x.x M   y 次 reshape，覆盖 z 条超大输出
  ② 剪枝臂（折价 × 后续请求） x.x M   y 次改写 / n 节点
  ③ 折叠臂（同机制）        x.x M   y 轮
  ④ 静态裁剪（前缀层）      x.x M   每请求 −3.7k（n 次）
  ⑤ 记忆注入开销（负项）    −x.x M  y 次
  净节省                  159.1M = 54.8%（上界口径）
  ── 单列 ────────────────────────────────────
  避免的击穿（piggyback）   72.6M   23 次改写落在冷窗口
  记忆臂（估算）            k 轮重复解释被替代 ≈ j 请求
  尾部集中度：fresh 的 50% 落在 1.7% 请求上；命中率 95.0%
```

| **P3** | 埋点复核：`static-trim` 用现有 `charsBefore/After`（进估算行）；`fold` 补 `payloadTokens`（avoided 兜底，契约测试锁定）；value 模型 avoided 兜底链 = 前置 usage 载荷 → `tokensBefore`/`payloadTokens` | ✅ 完成（avoided 70.9M → 73.7M，兜底生效） |
| **P4** | 价值段接入 `lcm report`（一行硬账）；交叉验证**脚本化**：模型内置载荷口径（`payload.pct`）与成本当量口径互证（ratio ∈ [0.3, 3]），`scripts/value-xcheck.mjs` 退出码 0/1 | ✅ 完成（实测 ratio 1.02：载荷 14.7% vs 成本 15.0%） |

## 8. 已知限制 / 不做

- 不做按 provider 的真实账单反推（不同家 cache 价不同）——只给 `--cache-factor` 区间（0.1 保守 / 1.0 上界）
- 不做「记忆臂值多少」的强口径（省的是轮次，因果链长）——只给估算并标注
- 不把 avoided 混进净节省（机会成本 ≠ 已实现收益）
