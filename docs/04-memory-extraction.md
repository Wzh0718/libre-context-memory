# 04 · 记忆提取设计（hot / warm / cold 三层 + 写入决策 + 同步）

> 与压缩的关系：**压缩解决「变短」，记忆提取解决「变有用」**。
> 压缩产物的摘要即记忆候选；记忆的存在让压缩可以更激进（关键事实已入持久层，压缩不怕丢）。

---

## 1. 三层记忆架构

| 层 | 内容 | 位置 | 体积策略 |
|---|---|---|---|
| **hot**（工作记忆） | 最近 N 轮原文 | 上下文尾部 | 不动 |
| **warm**（会话记忆） | 结构化摘要（折叠/压缩产物） | 上下文中部 | 有界（单块 ≤ 固定预算） |
| **cold**（持久记忆） | 事实/决策/偏好/未决/结论 | OpenViking（有配置）或项目级本地存储（无配置） | 按需检索注入，尾部追加稳定块 |

信息流：
```
hot ──(折叠/压缩)──> warm ──(提取+写入决策)──> cold
cold ──(检索注入)──> hot（下一轮请求尾部）
```

## 2. 什么算「记忆」（与「内容」严格区分）

| 类型 | 例子 | 来源 |
|---|---|---|
| **事实 facts** | 项目结构、路径、账号/配置位置、API 约定、版本号 | 对话、工具输出 |
| **决策 decisions** | 选了什么方案、为什么（附证据） | 对话 |
| **偏好 preferences** | 「改动范围最小」「插件优先」 | 用户表达 |
| **未决 open threads** | 未完成的事、待验证假设 | 对话 |
| **结论 conclusions** | 已验证的发现（「exec 占工具输出 81.9%」） | 分析产物 |
| **反模式 anti-patterns** | 已证伪的假设（「图片内联进上下文」） | 验证记录 |

**禁止写入**：secrets、瞬时状态、未验证猜测、可从代码重新发现的明显事实。提取器里硬编码过滤。

## 3. 提取时机与触发点（按 harness 能力对齐）

| 触发点 | DSH | CC | Codex | 提取对象 |
|---|---|---|---|---|
| 折叠前 | compaction seam | `PreCompact` | 待确认 | 将被折叠的旧历史 |
| 会话结束 | 插件 | `Stop` | `Stop` | 全会话未沉淀的结论 |
| 大工具输出压缩后 | toolResultPruner 管线 | PostToolUse 管线 | 同左（待探针） | 输出中的关键发现（错误、路径、计数） |

## 4. 提取方法（确定性优先，LLM 兜底）

**确定性启发式（零成本，先行）**：路径、命令、URL、版本号、错误码、决策关键词、文件改动清单。

**LLM 抽取（小模型）**：把「被折叠的历史 + 任务目标」交给抽取模型，输出结构化条目：

```json
{
  "type": "fact|decision|preference|open_thread|conclusion|anti_pattern",
  "subject": "gcli2api overlay",
  "claim": "src/converter/openai2gemini.py 本地副本落后上游，禁止拷入 custom-overlay",
  "evidence_refs": ["session:xxx", "event:yyy"],
  "confidence": 0.9,
  "ttl": "durable|session",
  "source_session": "..."
}
```

## 5. 写入决策（mem0 式，防污染的核心机制）

**写入不是 append，而是四选一决策**：

```
新条目 → 按 subject + 语义检索库内最相似 top-k → 判断：
  ADD    全新事实，直接写入
  UPDATE 同 subject 更新版 → 新覆盖旧（revision 语义，旧版进历史不丢）
  DELETE 新证据证伪旧条目 → 旧条目作废（如 anti_pattern 推翻 conclusion）
  NOOP   重复/等价内容 → 跳过
```

配套机制：
- **幂等键**：条目内容哈希作主键 → hook 重试/网络抖动不产生重复条目
- **本地 outbox**：cold 后端不可达时追加写 `outbox.jsonl`，hook 失败静默不阻塞主流程；下次任意壳启动时 flush，成功才删除
- **并发写入**（多个 harness 同时跑）：单条粒度 last-write-wins + confidence 比较；低 confidence 版本进 revision 历史

## 6. 同步：三个场景三种解法

| 场景 | 解法 |
|---|---|
| **跨 harness 同步**（CC ↔ Codex ↔ DSH） | 架构上免费：三个壳读写同一个 OpenViking 账号（或同一项目级本地目录），没有第二份拷贝，DSH 沉淀的记忆 CC 下次会话直接命中 |
| **写入一致性** | §5 的写入决策 + 幂等键 + outbox + revision |
| **跨机器** | OpenViking 是中心化服务天然支持；**spill 原文同理**：有 OpenViking 配置则上传 resources（跨机器可取），无配置则项目级本地（句柄带机器标识，跨机回取失败时明确提示） |

## 7. 注入（读取侧）——三条纪律

| 纪律 | 原因 |
|---|---|
| **尾部追加**稳定块，绝不插中间 | 插中间 = 前缀断裂 = 缓存打穿 |
| **预算有界**：top-k + 字符上限 | DSH 实测注入 2.9k est/请求可接受；注入本身不能成为体积源 |
| **只在相关时注入** | 无关注入既费 token 又误导模型 |

注入时机：DSH request-context 插件尾部注入；CC `SessionStart`/`UserPromptSubmit`；Codex `SessionStart`。
记忆库内容变了没关系——下一轮从尾部注入新版，**历史里的旧注入块不动**。

## 8. 与压缩的协同

| 协同点 | 说明 |
|---|---|
| 一次处理两次利用 | 压缩摘要直接进 warm；提取器从 warm 挑 durable 条目入 cold |
| 记忆让压缩更激进 | 关键事实已入 cold → 压缩阈值可以更低、更狠 |
| 压缩让注入更省 | 注入的是压缩后的稳定块而非原文 |

## 9. 现成数据基础（不用从零开始）

| 资产 | 用途 |
|---|---|
| Codex 354 份 `compacted` 摘要 | 现成 warm 层样本 → 校准「折叠什么、记什么」 |
| DSH 2,356 个注入段（99 唯一哈希） | 现成注入样本 → 校准注入预算与形态 |
| `~/.codex/memories/MEMORY.md`（252KB） | 现成用户记忆库 → 对齐 cold 层 schema |
| OpenViking（已运行，账号 default / 用户 libre） | cold 层存储与检索 |

## 10. 风险清单

| 风险 | 缓解 |
|---|---|
| 过度压缩 → 回取成本与失败 | 摘要保留行号锚点与关键词；回取失败计入记分卡 |
| 记忆污染（错误/过时事实入库） | §5 写入决策 + confidence + ttl + 只写已验证结论 |
| 注入自身成为体积源 | 预算有界 + 只在相关时注入 |
| 写入时机不当打断主流程 | hook 全异步、失败静默 + outbox 兜底 |
| 无 OpenViking 环境下体验缩水 | 明确降级语义：cold/spill 都落项目级本地，功能不少、范围缩小 |

## 项目作用域（注入隔离）· 2026-09-16

**问题**：记忆库是全局的（`~/.lcm/memories`），检索原本不做任何项目过滤 →
实测池化口径下 **22.7% 的注入槽位来自其它项目**（276 个外项目槽位），
且金标评测按同项目配对——「评测通过」并不能证明生产注入路径可用。

现场实证：`html_to_md` 的查询在池化口径下会召回 `libre_quant` 的交易规则
（「溢价规则说：禁止入场」、`/api/live` 现价判定）——跨项目串味直接进上下文。

**规则**（`memory.searchDetailed`）：

| 条目类型 | 作用域 |
|---|---|
| 任务事实（有 `project`，非画像） | **只召回同项目** |
| 无 `project` 条目（手动入库 / 全局约定） | 始终可选（设计上就是全局） |
| 画像条目（`profile: true`，自动晋升或 pin） | **始终可选**——跨会话「习惯画像」本来就该全局 |

- `projectScope: 'same'`（传了 `project` 时的默认）｜`'all'` = 旧的池化行为（显式跨项目）
- 项目键归一化：条目存 cwd（`/home/libre/project/x`），会话目录名是短横线形
  （`--home-libre-project-x--`），`normalizeProject` 统一（实现已从 eval 移入 memory 共用）

**实测收益**（金标库 61 对跨会话查询）：

```
池化口径：recall 98.4% ｜ 污染 22.7%（276 外项目槽位）
隔离口径：recall 100.0% ｜ 污染 0.0%（6154 条外项目候选被挡）
```

recall 反而**上升**——外项目条目原本就在挤掉正确条目。

**验收门**：`scripts/acceptance.mjs` 的金标门现在同时断言 `contamination === 0`
（评测与生产同口径）；契约测试锁定「同项目注入 / 全局注入 / 画像跨项目可见 / 外项目任务事实绝不注入」。
